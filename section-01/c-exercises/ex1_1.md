# Exercise 1.1: Improving matrix_transpose

1. **No error check.** `create_matrix` allocates memory and could fail. The function should check that `mt.data` is not NULL before writing to it.

2. **Unclear memory ownership.** The returned matrix holds heap memory, but nothing says who must `free` it. This should be documented, or the caller should pass in the output buffer.

3. **Better types.** Rows, columns and indexes can never be negative, so `size_t` fits better than `int`. With `int`, `i * m.cols + j` can overflow on very large matrices.

4. **Pass by pointer.** `m` is passed by value, so the struct gets copied. Using `const matrix_t *m` avoids the copy and guarantees the input is not modified.

5. **Cache performance.** Reads from `m.data` are sequential, but each write to `mt.data` jumps ahead by `m.rows`, which causes cache misses on large matrices. Processing the matrix in small blocks (tiling) keeps accesses close together.

6. **Embedded-friendly design.** On a microcontroller, allocating heap memory at runtime is risky because RAM is limited and the heap can fragment. A better design is `void matrix_transpose(const matrix_t *in, matrix_t *out)`, where the caller provides the output memory.
